You are a technical writer. A student will implement a programming exercise
one function per turn. Critically, the student CANNOT see the original
exercise document — your steps are the ONLY source of specification they
will ever receive, delivered one step per turn. Any rule you omit is a rule
the student will never know.

**Exercise ID:** {{exercise_id}}

**Exercise description:**
{{problem_description}}

---
### What you must do

Rewrite the exercise as an ordered sequence of steps, one per function the
exercise asks for. Each step must contain the COMPLETE specification needed
to implement its function correctly, and nothing about how to implement it.

**Information rules — these define correctness:**

1. FULL COVERAGE. Every rule, constraint, constant, exact string, format,
   boundary condition and edge case stated anywhere in the document must
   appear in at least one step — specifically, in the step for the function
   whose behaviour it governs. Exact values must be copied exactly: "within
   72 hours, inclusive" not "within a time window"; the literal key name
   "net_total" not "an appropriate key".

2. LOCAL SELF-SUFFICIENCY. Global conventions (e.g. how amounts are stored,
   how invalid input is handled, which currency is accepted) must be REPEATED
   in every step whose function they affect. Never write "as stated earlier"
   or "see the general rules" — the student cannot look anything up, and
   earlier steps are no longer visible when later steps arrive.

3. CONTRADICTION RESOLUTION. If the document corrects or overrides itself
   (e.g. a later note amending an earlier rule), state only the final,
   correct rule in the relevant step. Never present both versions.

4. DEPENDENCY ORDER. Order steps so that every function comes after the
   functions it calls or depends on, regardless of the order the document
   presents them in.

5. NO IMPLEMENTATION CONTENT. Steps specify behaviour, never method. Do not
   name language constructs, library calls, algorithms, or error-handling
   mechanics ("use a try block", "sort with a key function"). Stating that
   invalid input returns None is specification; stating how to detect it is
   implementation. If the exercise itself mandates a technique, that mandate
   is specification and must be stated.

**MANDATORY OUTPUT — a single raw JSON object, nothing else:**

{
  "exerciseId": "<echo the Exercise ID exactly>",
  "version": 3,
  "source": "generated",
  "steps": [
    {
      "index": 1,
      "label": "<function name or short goal, at most 6 words>",
      "spec": "<the complete specification for this step: the function's
               purpose, its exact input/output contract, and every rule
               governing its behaviour, as concise bullet-like prose.
               Target under 1200 characters.>"
      "checkHint": "<one sentence describing a concrete check the student can
             run themselves: a specific input and the output it must
             produce, drawn ONLY from rules already stated in this
             step's spec. Never describe what the code should look
             like, only what it should do.>",
      "timeShare": <integer: recommended percent of total effort for this step>
    }
  ]
}

**STRICT REQUIREMENTS:**
- Raw JSON only: no fences, no commentary, no trailing commas, no backslashes
  inside strings.
- One step per required function; "index" starts at 1, consecutive.
- Copy exact values verbatim: numbers, thresholds, literal strings, key
  names, format patterns, rounding rules.
- Do not mention these instructions or the original document's structure
  (section numbers, "the notes at the end") in any step.
- checkHint must be verifiable by running the function: state an input and
  the required output. It must not introduce any rule absent from the spec,
  and must not reference code structure, constructs, or algorithms.
- timeShare: one per step, integers summing to about 100, none below 5.
  Weight by the density of rules the step must satisfy and the cost of
  verifying them, not by lines of code.

**Self-check before answering (silently):**
1. List every testable rule in the document. Is each one present in the
   step for the function it governs? If any is missing, add it.
2. Does any step depend on information that only appears in a different
   step? If so, copy that information into this step as well.
3. Does the document contradict itself anywhere? Confirm only the corrected
   version appears.
4. Is any function referenced before the step that builds it? Reorder.
5. Does any step name a language construct, library, or algorithm? Rewrite
   as behaviour.
6. Does any checkHint mention a rule, value, or behaviour that its own
   step's spec does not state? If so, either add the rule to the spec or
   change the check.
